# 接入一个项目

插件是**开发期工具**：它运行在 DeepSeek Harness 里（Node），产出两类项目要消费的产物：

| 产物 | 放置位置 | 作用 |
| --- | --- | --- |
| `bridge-contract.json` | 版本控制 | 跨语言唯一共享的事实 |
| 生成的客户端或服务端骨架 | 版本控制 | 普通源码，由项目自己编译 |

**Java 项目不依赖这个插件，Python 项目也不依赖。** 它们依赖生成出来的代码。只有当项目在运行期还需要内置的 LangGraph 服务时，情况才不同——那是下面的模式 B。

## 三种模式

### A. 仅开发期（默认）

```
插件在 DSH 里跑  ->  生成源码  ->  提交  ->  项目照常构建运行
```

无运行时依赖，项目侧零配置。契约与生成代码都可评审，CI 也能发现漂移。

### B. 开发期 + 常驻服务

只有当项目的编排依赖内置 LangGraph 服务时才需要。三种持有者已实现，选一个：

| 持有者 | 做法 | 生命周期 |
| --- | --- | --- |
| 插件 | `bridge_service({ action: "start" })` | 插件卸载时停止 |
| 插件（脱钩） | `bridge_service({ action: "start", detached: true })` | 脱离会话存活，需显式停止 |
| 应用 | `lab.embed.autostart=true`、`lab.embed.root=<插件目录>` | 随应用起停 |

生产环境应当用第三种：应用启动服务、写 discovery 文件、退出时回收。discovery 文件是双方的约定——消费方读 `langgraph-service.json`，而不是写死端口。

除此之外不需要配置。`lab.langgraph.worker-base` 由 `server.address` 与 `server.port` **自动推导**，所以"忘了填"不会再变成"编排静默降级"；只有当服务看到的应用地址不同时才显式覆盖。

#### 用容器运行服务

插件自带 Dockerfile（`service/Dockerfile`，依赖钉在 `service/requirements.txt`）：

```sh
docker build -t polyglot-bridge-service:dev service
docker run -d --rm --name polyglot-service -p 8021:8021 \
  -v ${PWD}/service:/app -v polyglot-dev-data:/data \
  -e BRIDGE_DATA_DIR=/data polyglot-bridge-service:dev
```

应用侧要显式配置，因为容器里的 `127.0.0.1` 指容器自己：

```sh
LAB_GRAPH_BACKEND=langgraph \
LAB_LANGGRAPH_URL=http://127.0.0.1:8021 \
LAB_LANGGRAPH_WORKER_BASE=http://host.docker.internal:8525 \
LAB_EMBED_AUTOSTART=false \
mvn spring-boot:run
```

这里有两个容易错的点。挂载 `${PWD}/service:/app` 只覆盖源码、**不覆盖已安装的依赖**，所以依赖变更前构建的镜像会静默退化到内存检查点——改 `requirements.txt` 后必须重建镜像。另外 `BRIDGE_DATA_DIR` 必须是 volume：检查点是状态，不是产物。

### C. CI 里无头运行

生成器是普通 ES 模块，CI 不需要 DeepSeek Harness。写一个短包装即可：

```js
// scripts/generate.mjs
import { loadContractFile, writeFiles } from '@local/polyglot-bridge/lib/io.js'
import { generateJavaClient } from '@local/polyglot-bridge/lib/gen-java.js'

const [contract, outDir, packageName] = process.argv.slice(2)
const generated = generateJavaClient(loadContractFile(contract), { packageName })
writeFiles(outDir, generated.files)
```

然后两道 CI 门禁：

```sh
node scripts/generate.mjs contracts/orders.bridge.json src/main/java com.acme.orders.bridge
node ../polyglot-bridge/scripts/check-vendor.mjs          # 依赖树完整
node ../polyglot-bridge/scripts/check-typescript.mjs      # 若生成 TS 客户端
git diff --exit-code                                       # 生成代码是否为最新
```

最后一行就是漂移门禁：如果重新生成改动了被跟踪的文件，说明契约与代码已经不一致。

## 按项目类型

### Java / Spring

| 角色 | 目标 | 放置 |
| --- | --- | --- |
| 调用别的服务 | `java-client` | 独立包，例如 `com.acme.orders.bridge.client` |
| 被别的语言调用 | `java-server` | 生成的接口，在 `@RestController` 里实现 |
| 运行期需要编排 | 模式 B，应用持有 | `lab.embed.root` 指向插件目录 |

生成的客户端为契约声明的错误体提供 `ErrorBodies.decode(error)`，流式端点返回 `InputStream`。**不要手改生成的源码**，改契约后重新生成。

### Python / FastAPI

被调用方：挂载生成的 router。

```python
from orders.router import router as orders_router
app.include_router(orders_router, prefix="/api")
```

调用方：直接用生成的包。**没有第三方依赖**（只用 `urllib` 与 `dataclasses`），这在受限环境里很重要。流式端点是生成器，用 `for chunk in client.stream_thread(...)` 消费。

### Node / TypeScript

生成的 `src/client.ts` 只有类型与 `fetch`，无运行时依赖。放在 `src/api/` 下即可。需要鉴权或重试时，传入包装过的 `fetch`：

```ts
const client = new OrdersClient(baseUrl, (input, init) =>
  fetch(input, { ...init, headers: { ...init?.headers, authorization: token } }))
```

流式端点是 `AsyncGenerator`，用 `for await` 消费。

### 其他语言

提取对任何能导出 OpenAPI、能自述文档、或提供 Postman 集合的服务都有效。生成目前支持 Java、Python、TypeScript 客户端，以及 Java、Python 服务端骨架。所以 Go 或 C# 项目**今天可以作为被调用方**；等有对应生成器时才能作为调用方（见 `ADDING-A-LANGUAGE.md`）。

## 仓库布局

```
repo/
  contracts/orders.bridge.json     共享事实，像代码一样评审
  services/orders/                 服务，语言不限
  clients/web/                     生成的 TypeScript 客户端
```

三条规则：

1. **契约进仓库。** 它是双方唯一共同认可的东西。
2. **生成代码进仓库。** 评审能看到变更，CI 能发现漂移；构建时生成会把两者都藏起来。
3. **绝不手改生成文件。** 改契约并重新生成；手改会在下一次被覆盖。

## 反模式

| 不要 | 原因 |
| --- | --- |
| 让应用调用插件 | 它是 Node 模块，只存在于 DeepSeek Harness 内部 |
| 把插件做成构建期依赖 | 构建机通常没有 harness；用模式 C |
| 手改生成的客户端 | 会被覆盖；应当改契约 |
| 契约只留在插件缓存里 | 换机器即丢失，也无法评审 |
| 不核对就相信一份契约 | 从线上服务重新提取，并跑 `bridge_check` |

## 版本与漂移

- 生成文件在 README 里带 `generated by` 行，diff 可追溯到插件版本。
- **接受新文档之前**先用门禁：`bridge_check({ contractA: 当前, contractB: 候选, failOn: "breaking" })`。当候选删除了路由或模型、改了类型、收紧了必填时，调用会失败并打印计数。**在重新生成之前跑它**——破坏性变更需要的是迁移方案，不是一次新构建。
- **契约漂移**：部署后跑 `bridge_check(契约, "http://服务")`，能发现"部署了但没提交"和"提交了但没部署"。
- **代码漂移**：`bridge_check(契约, 项目目录)` 或上面的 `git diff --exit-code` 门禁，能发现契约改了但没重新生成。

## 新项目接入清单

1. 找文档：`bridge_discover({ projectDir })` 或 `bridge_discover({ url })`。
2. 提取：`bridge_extract(...)`，先读 `warnings` 再决定是否可信。
3. 提交 `bridge-contract.json`。
4. 为调用方生成客户端；若本项目是被调用方，再生成服务端骨架。
5. 编译生成物：`mvn compile`、`python -m compileall` 或 `tsc --noEmit`。
6. 把漂移门禁加入 CI（模式 C）。
7. 只有当项目运行期需要编排时：开启 `lab.embed.autostart` 并把 `lab.embed.root` 指向插件目录。
